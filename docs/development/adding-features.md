# Adding Features

Checklists for the most common extension points. Paths are relative to
`core/`. Work through the steps in order, since later ones build on
earlier ones.

---

## Adding a new REST endpoint

1. Write the handler in `crates/hc-api/src/handlers.rs`, or in a file
   of its own for a new resource type (auth routes go in
   `auth_handlers.rs`). Handlers take `State<AppState>`, a scope guard and
   their extractors, and return `impl IntoResponse`. `get_device` is a
   typical one:

   ```rust
   pub async fn get_device(
       State(s): State<AppState>,
       _: DevicesRead,
       Path(id): Path<String>,
   ) -> impl IntoResponse {
       match s.store.get_device(&id).await {
           Ok(Some(device)) => (
               StatusCode::OK,
               Json(json!(normalize_native_device_type(device))),
           ),
           Ok(None) => (
               StatusCode::NOT_FOUND,
               Json(json!({ "error": "device not found" })),
           ),
           Err(e) => (
               StatusCode::INTERNAL_SERVER_ERROR,
               Json(json!({ "error": e.to_string() })),
           ),
       }
   }
   ```

   If it needs a new `StateStore` method, add it to the right `*_store.rs`
   file in `crates/hc-state/src/` and expose it from `StateStore` in that
   crate's `lib.rs`.

2. Register the route in `router()` in `crates/hc-api/src/lib.rs`.
   Paths are relative to `/api/v1`, which the router nests everything
   under, and use axum 0.8's `{param}` syntax. Put the route in
   `protected` (behind `require_auth`) unless it must be reachable without
   a bearer token, in which case it goes in `public` and checks auth
   itself.

   ```rust
   .route("/my-resource/{id}", get(handlers::get_my_resource))
   ```

3. Guard it with a scope. Each guard is a typed extractor generated by
   `scope_extractor!` in `crates/hc-api/src/auth_middleware.rs`
   (`DevicesRead`, `AutomationsWrite`, `PluginsWrite` and so on). Adding
   one as a handler parameter rejects the request with 403 before the body
   runs. A new permission needs a new `scope_extractor!` line, and the
   scope must be granted to the right roles in `Role::scopes()` in
   `crates/hc-auth/src/user.rs`.

4. Document it in `docs/openapi.yaml`: path, methods, parameters,
   request and response shapes, status codes, and the scope the guard
   requires. The spec is hand-maintained.
   `homecore/tests/openapi_covers_router_test.rs` compares its paths with
   the `.route(...)` calls and fails when they differ.

5. Write tests. Unit tests go in a `#[cfg(test)]` module beside the
   code. End-to-end checks of scopes and sessions live in
   `homecore/tests/`.

   ```bash
   cargo test -p hc-api
   cargo test -p homecore --test openapi_covers_router_test
   ```

## Adding a new action type

1. Add the variant to the `Action` enum in
   `crates/hc-types/src/rule.rs`. Rules are stored as RON, and the enum
   uses serde's default external tagging (no `#[serde(tag)]`).

   ```rust
   pub enum Action {
       // ... existing variants ...
       MyNewAction {
           device_id: String,
           value: JsonValue,
           #[serde(default)]
           some_option: bool,
       },
   }
   ```

   Put `#[serde(default)]` on optional fields so rule files without them
   still deserialize. You don't need an `enabled` field: every step is
   wrapped in `RuleAction { enabled, action }`, and the executor records a
   disabled step as `Skipped` on its own.

2. Add the match arm to `run_single_action()` in
   `crates/hc-core/src/executor.rs`. It returns a boxed future of
   `Result<()>`, so an arm does its work and returns `Ok(())` or an error.
   The executor turns that into the step's `ActionTrace` outcome (`Ok`, or
   `Error { message }`).

   ```rust
   Action::MyNewAction { device_id, value, .. } => {
       // ctx.publish  — MQTT publish handle (device commands)
       // ctx.event_bus — the typed event bus (pub_bus)
       // ctx.state    — the state store, when present
       // ctx.device_cache — live device attributes
   }
   ```

3. Describe it for traces in the helpers near the end of
   `executor.rs`: `action_type_name()` and `action_description()`. Both
   are exhaustive matches, so the compiler points at them.

4. Write unit tests in `executor.rs`. The `RepeatUntil` and `Delay`
   tests are good templates.

   ```bash
   cargo test -p hc-core
   ```

5. Regenerate the rule vocabulary. `GET /automations/vocabulary` is
   derived from the enums, and a snapshot test fails until the committed
   `docs/rule-vocabulary.json` matches:

   ```bash
   UPDATE_VOCABULARY=1 cargo test -p hc-types --features schema
   ```

6. Document it: the action reference in `docs/devNotes.md`, and
   [Actions](../rules/actions.md) on this site.

## Adding a new trigger type

1. Add the variant to the `Trigger` enum in
   `crates/hc-types/src/rule.rs`.

   ```rust
   pub enum Trigger {
       // ... existing variants ...
       MyNewTrigger {
           some_field: String,
       },
   }
   ```

2. Add matching in `crates/hc-core/src/engine.rs`. Two functions are
   involved:
   - `trigger_kind_can_match_event()` is a cheap pre-filter that says
     which event variants a trigger kind could ever match. Return `true`
     for your trigger on the events it listens to.
   - `trigger_check(trigger, event)` decides the match and returns
     `TriggerResult::Matched` or `TriggerResult::NoMatch(reason)`.

   ```rust
   (Trigger::MyNewTrigger { some_field }, Event::Custom { event_type, .. })
       if event_type == some_field => Matched,
   ```

3. Decide where the event comes from. Typed events (including the
   scheduler's and the managers') travel on `pub_bus`. Only raw MQTT
   (`Event::MqttMessage`) travels on `internal_bus`. Time-based triggers
   are not matched against events at all: the scheduler fires them
   directly with a synthetic `scheduler_tick` event, so they belong in
   `crates/hc-core/src/scheduler.rs`, along with any catch-up behaviour on
   restart.

4. Write unit tests covering both match and no-match cases. The
   engine's test module has many examples
   (`webhook_trigger_matches_correct_path` and its neighbours).

   ```bash
   cargo test -p hc-core
   ```

5. Regenerate the rule vocabulary as for actions.

6. Document it in `docs/devNotes.md` and
   [Triggers](../rules/triggers.md), with the required fields and a RON
   example.

## Adding a new condition type

1. Add the variant to the `Condition` enum in
   `crates/hc-types/src/rule.rs`.

   ```rust
   pub enum Condition {
       // ... existing variants ...
       MyNewCondition {
           device_id: String,
           attribute: String,
           expected_value: JsonValue,
       },
   }
   ```

2. Add the evaluation to `evaluate_one()` in
   `crates/hc-core/src/engine.rs`. It is async and returns
   `Result<(bool, ConditionTrace)>`. Read device state from the
   `snapshot` it is given, a map of device ID to attribute object built
   from the engine's in-memory device cache, not from redb. Conditions
   must have no side effects.

   ```rust
   Condition::MyNewCondition { device_id, attribute, expected_value } => {
       let actual = snapshot
           .get(device_id)
           .and_then(|attrs| attrs.get(attribute))
           .cloned()
           .unwrap_or(JsonValue::Null);
       let passed = actual == *expected_value;
       Ok((passed, ConditionTrace {
           condition_type: "MyNewCondition".into(),
           passed,
           actual: Some(actual),
           expected: Some(expected_value.clone()),
           reason: format!("{device_id}.{attribute} (expected {expected_value})"),
       }))
   }
   ```

3. Add the dry-run arm to `eval_condition_dry_detail()` in
   `crates/hc-api/src/handlers.rs`. That function backs
   `POST /automations/{id}/test` and evaluates conditions separately from
   the engine. It is an exhaustive match, so the build fails until you add
   it.

4. Write unit tests.

   ```bash
   cargo test -p hc-core
   ```

5. Regenerate the rule vocabulary, then update `docs/devNotes.md` and
   [Conditions](../rules/conditions.md).

## Adding a new notification channel

1. Create `crates/hc-notify/src/<name>.rs` with a `<Name>Config`
   struct (`#[derive(Deserialize)]`) and a channel type that implements
   `NotifyChannel` from `channel.rs`:

   ```rust
   #[async_trait]
   pub trait NotifyChannel: Send + Sync {
       async fn send(&self, title: &str, message: &str) -> Result<()>;
   }
   ```

2. Add a variant to `ProviderConfig` in `crates/hc-notify/src/lib.rs`.
   It is tagged by `type`, lowercased, so the variant name becomes the
   `type = "..."` value in `[[notify.channels]]`.

3. Add a build arm in `NotificationService::from_configs` that
   constructs the channel and calls `svc.register(name, channel)`.

4. Add `pub mod <name>;` to `lib.rs`.

Config parsing, the executor and the rule engine need no changes. Then
update [Notifications](../events/notifications.md) with setup
instructions.

## Adding a new device type

`device_type` is a free-form string that a plugin sends at registration.
There is no list of constants in code. The doc comment on `device_type`
in `crates/hc-types/src/device.rs` gives examples (`"switch"`, `"light"`,
`"motion_sensor"`, `"virtual_switch"`), and UIs use the field to
categorize devices and to separate scenes (`device_type = "scene"`) from
controllable devices.

If an operator has a `config/profiles/device-types.toml`, a registration
that carries a `device_type` named in it gets that type's built-in schema
(see `crates/hc-topic-map/src/device_types.rs`). An example catalog ships
in `config/profiles/examples/device-types.toml`.

When you introduce a new type:

1. Update the device type section of
   [Developing plugins](../plugins/developing-plugins.md#device-type-field).
2. Add an entry to the example `device-types.toml` if mapped devices
   should get a schema for it.
3. Update [Scenes](../devices/scenes.md) if it affects how scenes are
   filtered.

## Testing patterns

### Unit tests

Put a `#[cfg(test)] mod tests` block at the bottom of the file under
test. Use `#[test]` for synchronous tests and `#[tokio::test]` for async
ones.

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn my_sync_test() {
        assert_eq!(1 + 1, 2);
    }

    #[tokio::test]
    async fn my_async_test() {
        // async code here
    }
}
```

An executor test needs an `ExecutorContext`. It has many fields (the
publish handle, notifier, event bus, device cache, delay registry, rule
variables, capture store, hub variables, trace buffer and more), so copy
the construction from an existing test in `executor.rs` instead of
writing it from scratch.

### Integration tests

Integration tests live in `homecore/tests/`. `integration_test.rs` starts
an embedded broker on a free port (`free_port()`), opens a state store in
temp files, writes a rule into it, starts `Core`, publishes a device
state over MQTT and asserts that `DeviceStateChanged` and `RuleFired`
arrive. Subscribe to the event bus before publishing anything, or you
will miss events. Add scenarios as `#[tokio::test]` functions in that
file or in a new file beside it.

```bash
cargo test -p homecore --test integration_test
```

### Dry run through the API

Evaluate a rule's conditions without running its actions:

```bash
curl -s -X POST http://localhost:8080/api/v1/automations/{id}/test \
  -H "Authorization: Bearer $TOKEN" | jq
```

The response has `conditions_pass`, `would_fire`, the rule's `actions`,
and one entry per condition with `condition`, `passed`, and where they
apply `actual`, `expected`, `elapsed_ms` and `reason`. Add `?at=` with a
time (`22:30`) or a date and time to judge the conditions at that moment.
Only the clock moves; the devices stay as they are now. `POST /automations/test` does the same for an unsaved rule sent in
the body.
